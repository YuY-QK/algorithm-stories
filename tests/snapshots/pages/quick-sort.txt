亲手写

在自己电脑上用 IntelliJ IDEA 或 Android Studio 打开仓库里的 exercises/ 目录，把 quicksort/QuickSort.kt 里的三个 TODO() 换成你的代码：

partition(arr, lo, hi)：Lomuto 分区，最后一个当标杆，返回标杆落的下标。测试检查左边都比它小、右边都不比它小、区间外没被动过。
quickSort(arr)：原地排成升序。测试里有 3000 个已经排好的数和 3000 个全一样的数，别让它退化得太慢或栈溢出。
quickSelect(arr, k)：第 k 小的数（k 从 1 开始），只处理有答案的那一边，平均 O(n)。测试会在 100 万个数里找中位数。

快还是慢，看标杆选得好不好

每次分区要把区间里每个数和标杆比一次。标杆把区间分得越均匀，递归的层数越少：平均情况约 1.39 · n · log₂n 次比较，是 O(n log n)。最坏情况是每次标杆都是最大或最小，一层只站定一个，比较 n(n − 1)/2 次，是 O(n²)，递归也有 n 层深。下面是「已经排好」的数组，用三种办法选标杆的比较次数：

条形长度用对数刻度绘制。固定拿最后一个，一万个有序数要比较近五千万次；随机或三数取中只要十几万次，差了三四百倍。

🛡️
怎么躲开最坏情况
随机标杆：随机挑一个换到末尾再分区，没有哪种输入能稳定地让它退化，期望还是 O(n log n)。
三数取中：取区间最左、正中、最右三个数的中位数当标杆，对已经有序或倒序的数组正好选到中间。
先递归短的一边：长的一边用循环接着做，递归深度不超过 log₂n，不会栈溢出。「亲手写」的参考答案就是这样写的。
重复很多时：Lomuto 把相等的都放到一边，全是相同的数时会退化成 O(n²)。三路分区（小于、等于、大于）一次把相等的都站定，解决这个问题。
🧳
原地，但不稳定
原地：只在数组里换位置，额外空间主要是递归栈，平均 O(log n)，最坏 O(n)。
不稳定：分区时隔着很远的交换，会让相等的元素换了先后顺序。要稳定就选归并排序，或者给每个元素带上原来的位置当第二关键字。
缓存友好：分区是顺着数组一路扫过去，访问很连续，所以实际速度通常比同样 O(n log n) 的堆排序快。
🌍
真实世界里的快速排序
Java 的 Arrays.sort(int[]) 用的是双轴快速排序（Dual-Pivot Quicksort）：选两个标杆，一次分成三段。Kotlin 的 IntArray.sort() 在 JVM 上就是调它。长度很小的区间改用插入排序；较新的 JDK（14 起重写）递归太深时还会切换成堆排序，保住 O(n log n)。对象数组用的是稳定的 TimSort。
C++ 的 std::sort 常见实现是 introsort：快速排序递归太深时切换成堆排序，保住 O(n log n)，小区间收尾用插入排序。
Go 的 sort 包和 Rust 的 sort_unstable 用的是 pdqsort 一类改良快排：自动发现有序、倒序、重复很多的情况。
快速选择是同一个分区思路：C++ 的 std::nth_element 就是它的实现（introselect）。只要中位数、前 k 名，不用把全部排好。
