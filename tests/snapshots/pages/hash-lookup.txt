为什么快

存、取、删都先算桶号，再只看那一个桶。哈希函数分得匀、表不太满时，一个桶里平均只有一两本书，所以平均时间是 O(1)，和书有多少无关。顺序查找平均要看一半的书：

📉
最坏情况和扩容
最坏 O(n)：所有键都撞进同一个桶，退化成顺序查找。挑战里书号有规律、书架数选得不好，就是这种样子。
负载因子 = 元素个数 ÷ 桶数。链地址法可以大于 1；线性探测必须小于 1，越接近 1 探测越长，一般装到约一半到四分之三就扩容。
扩容：容量翻倍，每个键要用新容量重新算桶号（找 bug 里的第三个坑）。一次扩容是 O(n)，但每次翻倍，摊到每次插入还是 O(1)。
哈希表不保持大小顺序，不能高效找最小最大，也不能做范围查询。要范围查询用二分查找（要求有序，O(log n)）或 B 树。
🌍
真实世界里的哈希表
Java 和 Kotlin/JVM 的 HashMap：默认容量 16、装到四分之三就扩容为 2 倍；链地址法，链太长时转成红黑树。
Redis 的键空间是一张哈希表，扩容时把搬家分散到后面的多次操作里（渐进式 rehash），免得一次卡住服务。
数据库的哈希索引只适合「等于」查询；范围查询用 B 树。哈希连接把一张表建成哈希表，再逐行去查另一张表。
缓存按键存取（LRU 缓存里的「键到节点」就是哈希表）；用 HashSet 去重；「两数之和」用 HashMap 记下见过的数，把 O(n²) 降到 O(n)。
🛠️
Kotlin 里怎么用

直接用标准库：mutableMapOf()（按插入顺序遍历的 LinkedHashMap）、HashMap、HashSet。键要用不可变的类型，自定义类当键时 equals 和 hashCode 要一起重写，data class 会自动生成。不要依赖遍历顺序。
