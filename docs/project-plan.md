## 1. 愿景和定位

**一句话**：让学习算法变得简单有趣。每个算法是一个有角色、有场景的小故事，配一个能亲手玩的演示，从小朋友到 IT 从业者都能找到适合自己的那一层。

**和现有产品的区别**

| 现有产品 | 它擅长的 | 我们补的 |
|---|---|---|
| VisuAlgo、Algorithm Visualizer | 专业、完整的可视化 | 没有故事，入门门槛高，不面向小朋友 |
| LeetCode、力扣 | 刷题、面试 | 不讲「为什么」，缺少直观感受 |
| 少儿编程平台（如 Scratch 类） | 低龄、好玩 | 算法内容浅，不衔接到工程 |

我们的定位：**同一个算法，从故事一路讲到工程**。小朋友停在故事和动手玩，工程师继续往下看代码、复杂度和真实系统里的用法。

**三条产品原则**

1. 先有趣，再严谨：每页先让人想玩，但每一步动画都必须和真实算法执行一致。
2. 一个算法，四层深度：同一个故事贯穿四个等级，越往后越深，而不是四套无关的内容。
3. 内容和产品一体：同一份故事稿既是网站上的页面，也能直接发博客，一次创作多处使用。

## 2. 用户和等级

| 等级 | 对象 | 学习方式 | 一页里看到什么 | 衡量「学会了」 |
|---|---|---|---|---|
| 初级 | 小朋友（约 6～12 岁，家长陪同） | 故事加点选、拖拽，不写代码 | 角色、场景、动手玩 | 能用自己的话讲出规则，能在游戏里做对 |
| 进阶 | 初学者、青少年 | 可视化加积木式拼逻辑 | 动画、拼步骤 | 能把步骤按正确顺序拼出来 |
| 中级 | 在校生、转行者 | 可视化加简单代码，自动评测 | 动画、代码填空、复杂度直观对比 | 能补全代码并通过测试 |
| 高级 | IT 从业者 | 逐步执行、真实代码、性能对比、工程场景 | 指针和代码同步、复杂度、易错点、真实系统 | 能说出易错点和工程取舍 |

**每个算法页的统一结构（四段）**

```
生活场景（故事）  →  动画演示  →  自己动手  →  代码与复杂度
   初级停在这里 ─────────┘           │              │
   进阶、中级走到这里 ────────────────┘              │
   高级走完全程 ──────────────────────────────────────┘
```

**游戏化**：每个等级都有进度、星星和徽章。初级偏画面和角色收集，高级偏挑战（比如「用最少比较次数找到目标」）和排行。

**次要用户**：家长和老师（给孩子选内容、拿去课堂用），博客读者（从文章跳到演示）。

## 3. 产品形态

### 3.1 网站结构

```
首页
├── 等级地图：选一个等级，看到按难度排好的学习路线
├── 算法库：按分类浏览（查找、排序、数据结构、图、算法思想、工程常用）
├── 算法页 /algo/<slug>?level=kid|beginner|mid|pro
│     故事 · 演示 · 动手 · 代码（按等级显示不同深度）
├── 故事集（博客）：每篇故事稿的文章版，文末链接到演示
└── 我的进度：星星、徽章、已学算法（先存在本机浏览器里）
```

### 3.2 现状

- 已完成：二分查找（小邮差找信箱）、冒泡排序（排队拍合照），都只有初级和高级两档。
- 每个算法是一个约 600 行的单文件 HTML，样式和脚本内联，互相之间没有共享代码。
- 两个算法目录里都还没有 `notes.md`（资料整理那一步被跳过了）。
- 没有首页，没有 git，没有 GitHub 仓库。

单文件做原型很合适，但按清单的约 30 个算法、每个最多四档来算，配色、等级切换、逐步执行面板、代码高亮会被复制几十遍，改一次风格要改 30 个文件。所以规模化之前需要一次架构升级，见第 4 节。

## 4. 技术架构

### 4.1 分层

把每个演示拆成三层（最初的设想；阶段 R 之后细分为配置、规则、流程、主题、界面，现行分层见 `docs/level-spec.md` 末节）：

```
┌──────────────────────────────────────────────────────┐
│ 内容层   故事稿 story.md、资料 notes.md、算法元数据       │  ← 写一次，网站和博客共用
├──────────────────────────────────────────────────────┤
│ 界面层   各等级的交互组件（初级游戏、高级逐步执行面板）     │  ← 网页、PWA、App 共用
│          共享组件：等级切换、播放控制、代码高亮、主题        │
├──────────────────────────────────────────────────────┤
│ 引擎层   每个算法一个纯函数：输入 → 每一步的状态列表        │  ← 不碰界面，可测试，可复用
└──────────────────────────────────────────────────────┘
```

**引擎层的统一数据格式**（所有算法都输出这种「步骤轨迹」，界面只负责播放）：

```ts
// 所有算法共用的字段（src/engine/types.ts）
interface Step {
  line: number;   // 对应参考代码的行号，用于高亮
  note: string;   // 这一步发生了什么，给人看的一句话
  done: boolean;  // 是否最后一步
}
// 每个算法在此基础上加自己的状态，例如二分查找：
interface BinaryStep extends Step { lo: number; hi: number; mid: number | null; count: number; found: number }
```

有了这个约定，播放控制、单步、调速、代码行高亮、比较次数统计都只写一次，新算法只要写引擎函数和这个算法独有的画面。

### 4.2 技术选型（建议，待决定）

| 方面 | 建议 | 理由 | 备选 |
|---|---|---|---|
| 网站框架 | **Astro**（已定） | 天生适合「内容加互动」：故事稿是 Markdown 直接变页面，演示作为可交互组件嵌入；输出纯静态文件，放 GitHub Pages 免费 | — |
| 交互组件 | **Vue 3 + TypeScript**（已定） | 你熟悉 Vue，能自己看懂和修改；App 走 Capacitor 打包，和 React 差别不大 | React（备选，未采用） |
| 动画 | SVG 为主，网格类（迷宫）用 Canvas | SVG 好做无障碍和深浅主题；大网格用 Canvas 更流畅 | — |
| 样式 | 沿用现有配色变量，抽成一个共享主题文件 | 保持两个原型的视觉风格 | — |
| 参考实现 | 继续用 Python，带自测 | 读者最熟悉，适合博客贴代码 | 加 JS/Java 版本（后期） |
| 测试 | 引擎函数单元测试，并和 Python 参考实现对拍 | 保证「动画每一步和真实算法一致」 | — |
| 部署 | GitHub Actions 自动构建，发布到 GitHub Pages | 免费，推送即上线 | Vercel、Cloudflare Pages（国内访问可能更好，待核实） |
| 进度存储 | 第一阶段存在浏览器本地 | 不需要后端和账号，先验证内容 | 后期加账号同步（见第 7 节 P4） |

### 4.3 目录结构（升级后）

```
algorithm/
├── content/algorithms/<slug>/
│   ├── meta.json        名称、分类、等级、故事标题、状态
│   ├── notes.md         资料（algorithm-researcher 产出）
│   ├── story.md         故事稿（网站页面和博客共用）
│   └── <name>.py        Python 参考实现加自测
├── src/
│   ├── engine/<slug>.ts 引擎：纯函数，输出 Step[]
│   ├── components/
│   │   ├── shared/      播放器、等级切换、代码面板、主题
│   │   └── <slug>/      该算法独有的画面（初级游戏、高级视图）
│   └── pages/           首页、等级地图、算法页、故事集
├── tests/               引擎测试、和 Python 对拍
├── prototypes/          现有两个单文件原型，留作参考
├── docs/                规划、清单、对话记录
└── .claude/agents/      四个 agent
```

现有的 `algorithms/` 两个目录迁移时内容放进 `content/`，原型 HTML 移到 `prototypes/` 保留，链接不丢。

### 4.4 从网页到 App

| 阶段 | 做法 | 改动量 |
|---|---|---|
| 网页 | Astro 静态站 | — |
| PWA | 加上 manifest 和离线缓存，可「添加到主屏幕」，离线可玩 | 小 |
| App 上架 | 用 Capacitor 把同一份网页打包成 iOS、Android 应用 | 中，主要是图标、启动页、商店审核 |
| 原生体验（如有需要） | 只在确有必要时用 Flutter 等重写界面层，内容和引擎原样复用 | 大，只在确有必要时做 |

引擎层和界面层不依赖浏览器特有功能，所以这条路线上代码基本不用重写。

## 5. 内容生产流水线

### 5.1 每个算法的流程

```
选题（清单）→ 资料 notes.md → 故事 story.md → 引擎 + 演示 → 审校 → 发布网站 → 改写成博客 → 记录反馈
 你决定        researcher      story-writer     demo-builder   reviewer   自动部署     （新增）      你
```

建议调整：

1. **不跳过资料这一步**：给二分查找和冒泡排序补上 `notes.md`，以后每个算法都先有它，故事和代码都以它为事实依据。
2. **加一个「博客改写」步骤**：把 `story.md` 按平台改写（标题、开头、配图、文末链接演示），可以新增一个 agent，或者由 story-writer 顺带产出。
3. **四个 agent 的说明要随架构升级更新**：demo-builder 改成写 `src/engine/<slug>.ts` 和组件，而不是单文件 HTML。

### 5.2 「完成」的标准

一个算法在某个等级算完成，需要同时满足：

- [ ] `notes.md` 有出处，不确定的地方标了「待核实」
- [ ] 故事里的每一步和引擎输出一致（有测试）
- [ ] 引擎对大量随机输入的结果与 Python 参考实现一致
- [ ] 浅色、深色主题和手机宽度都检查过
- [ ] content-reviewer 审校没有「必须修改」项
- [ ] 清单 `docs/algorithm-catalog.md` 和首页已更新

### 5.3 内容顺序

沿用清单里的建议：先做 BFS 走迷宫（检验架构对「网格类」算法是否适用），再补初级能玩的内容（顺序查找、选择排序、栈、队列、贪心），凑够 8 到 10 个后上线首页和开始发博客。

## 6. 发布

### 6.1 GitHub

- 仓库：一个公开仓库，放全部代码和内容，README 里放在线演示链接和动图。
- 网站：GitHub Actions 每次推送自动构建，部署到 GitHub Pages。
- 许可证（待决定）：建议代码用 MIT，故事和图片等内容用 CC BY-NC-SA 4.0（允许转载和改编，需署名，不得商用）。
- 规范：`main` 分支即线上版本，每个算法一个分支和一个 PR。

### 6.2 博客

| 平台 | 读者 | 适合发什么 |
|---|---|---|
| 掘金、CSDN、博客园 | 开发者 | 高级向：故事加代码、易错点、工程应用 |
| 知乎 | 学生、转行者、开发者 | 中级向，适合做成专栏 |
| 微信公众号 | 家长、泛读者 | 初级向故事，配动图，链接到演示 |
| 小红书、B 站（可选） | 家长、学生 | 演示录屏短视频 |

建议节奏：上线首批 8 到 10 个算法后开始，每周 1 篇，形成「算法小故事」系列。每篇文末链接对应演示页和 GitHub。

### 6.3 衡量效果

先看三个数：演示页访问量和停留时长、GitHub Star、博客阅读和收藏。网站统计工具待决定（需考虑国内可访问性和隐私）。

## 8. 风险

| 风险 | 应对 |
|---|---|
| 内容量大，一个人做不完 | 流水线加 agent 分工；每个算法先只做初级和高级，进阶、中级后补 |
| 动画和真实算法不一致，误导读者 | 引擎统一输出步骤，测试对拍 Python 参考实现 |
| 初级对小朋友是否真的有趣，还没验证 | P1 期间找几个孩子实际试玩，记录反馈 |
| GitHub Pages 国内访问不稳定 | 必要时加一个国内镜像或换托管（待核实） |
| 架构升级拖慢出内容 | P0 限定在 2 周，迁移完立刻做新算法 |
| 面向儿童的隐私合规 | P4 前不收集任何个人信息，进度只存在本机 |
