# 哈希查找：资料

## 1. 解决什么问题

不用一个个翻、也不要求排好序，凭「键」直接算出东西放在哪，一步走到位地存、取、删。

## 2. 核心思路

1. 准备一排编了号的「桶」（数组），桶数叫容量，比如 7。
2. 用哈希函数把键算成桶号：`index = hash(key) % 容量`。教学里用整数键，`hash(key) = key`，即 `key % 容量`，结果可预测。
3. 存和取都先算桶号，再只看那一个桶，不看别的桶。
4. 两个键算出同一个桶叫冲突，用两种办法之一解决：
   - 链地址法：每个桶挂一串（链表），撞了就接在后面，查时只在这一串里找。
   - 开放寻址（线性探测）：桶被占了就往后一格看，直到找到空桶；查时同样从算出的桶开始往后找，遇到空桶才说明不存在。
5. 装得太满就变慢，所以数据变多时要扩容：容量翻倍，所有键按新容量重新算桶号。

## 3. 复杂度和性质

| 项目 | 值 |
|---|---|
| 查找、插入、删除（时间，最好、平均） | O(1)，前提是哈希函数分得匀、负载因子受控（平均情况是在这个假设下的期望） |
| 时间（最坏） | O(n)，所有键撞进同一个桶，退化成顺序查找 |
| 空间 | O(n)，另加一些空桶，要拿空间换时间 |
| 扩容 | 一次扩容 O(n)，但容量每次翻倍，摊还到每次插入仍是 O(1) |
| 有序性 | 不保持键的大小顺序，不能高效做范围查询、找最小最大 |

**负载因子** = 元素个数 / 桶数，写作 α。

- 链地址法：α 可以大于 1，平均链长就是 α。
- 线性探测：α 必须小于 1（桶总数有限），而且 α 越接近 1，探测越长，一般在 0.5 到 0.75 左右就扩容。
- Java `HashMap` 默认容量 16、负载因子 0.75，元素数超过 容量 × 0.75 就扩容为 2 倍。

**好的哈希函数**

- 确定：同一个键永远算出同一个值。
- 均匀：不同的键尽量分散到各个桶。`key % 容量` 对有规律的键（例如全是 10 的倍数、容量又是 10）会全撞进一个桶，所以容量常选质数，或像 Java 那样先把高位混进低位。
- 快：算一次不能比顺序翻一遍还贵。
- 相等的键必须算出相等的哈希值（反过来不要求）。

## 4. 常见变种和易错点

**变种**

- 链地址法：链表换成别的结构。Java 8 起，`HashMap` 某个桶的链长到 8 且桶数不少于 64 时，把链表转成红黑树，最坏情况降到 O(log n)。
- 开放寻址的探测方式：线性探测（每次 +1，实现最简单，但容易出现一大片连续被占的桶）、二次探测（步长 1、4、9……）、双重哈希（步长由第二个哈希函数决定）。
- 删除：开放寻址不能直接把桶清空，要打「墓碑」标记。
- 其他：`HashSet`（只存键）、保持插入顺序的 `LinkedHashMap`、一致性哈希（见目录中的「一致性哈希」）。

**易错点（代码层面）**

1. 负数取模。Kotlin、Java 里 `-3 % 7` 是 `-3`，不是 `4`，直接当下标会越界。要用 `Math.floorMod(key, cap)` 或 `((key % cap) + cap) % cap`。
2. 线性探测删除时直接把桶置空。后面原本因为冲突排在它后面的键，查找时在这个空桶就停了，被「断链」，明明在表里却查不到。要用墓碑：删除时标成「已删除」，查找时跳过继续往后，插入时可以复用。
3. 线性探测往后一格不回绕。`i + 1` 要写成 `(i + 1) % cap`，否则探测到数组末尾越界，也漏掉排在表前面的空桶。
4. 扩容时直接把旧下标搬到新数组。容量变了，`key % 容量` 的结果也变，必须逐个键用新容量重新算桶号（重新插入）。
5. `put` 时没先查键是否已存在，直接往链上追加，同一个键出现两份，`get` 取到旧值，`size` 也偏大。
6. 开放寻址的表被填满后，查找一个不存在的键，会一直转圈不遇到空桶。要么在 α 到阈值前扩容，要么限制探测次数不超过容量。
7. 用可变对象当键。把对象放进 `HashMap` 后又修改参与 `hashCode` 的字段，它的哈希值变了，之后按这个键去取，会去错误的桶，找不到。键应当是不可变的（`String`、`Int`、Kotlin `data class` 里的 `val` 字段）。
8. `equals` 和 `hashCode` 不一致。自定义类只重写了 `equals` 没重写 `hashCode`，两个「相等」的对象会落进不同的桶，查不到。规则：`a == b` 则 `a.hashCode() == b.hashCode()`。Kotlin 的 `data class` 会自动一起生成。
9. 依赖遍历顺序。`HashMap` 不保证遍历顺序，扩容后顺序还可能变，代码和测试不能依赖它；要有顺序用 `LinkedHashMap`（Kotlin 的 `mutableMapOf()` 返回的就是它，按插入顺序）或排序后再用。

## 5. 真实应用

**生活**

- 图书馆按索书号找书：号码直接告诉你在哪个书架、哪一层，不用把书一本本翻过去。
- 酒店、学校的编号储物柜或信箱：房号、学号对应固定的格子；两人同格时再「往后一格」就是线性探测的样子。

**工程**

- Java / Kotlin 的 `HashMap`：Kotlin 在 JVM 上的 `HashMap`、`HashSet` 就是 `java.util` 的版本。桶数是 2 的幂，用 `(n - 1) & hash` 取桶号，并先把哈希值的高 16 位混进低 16 位（`h ^ (h >>> 16)`）；链地址法，链长过长转红黑树；默认负载因子 0.75。
- Redis 的键空间：Redis 的数据库本质是一张哈希表（`dict`），链地址法解决冲突，扩容时采用渐进式 rehash，把搬迁分散到后续的多次操作里，避免一次扩容卡住服务。
- 数据库索引：很多数据库提供哈希索引（例如 PostgreSQL 的 `CREATE INDEX ... USING hash`），只适合等值查询（`=`），不能做范围查询；范围查询用 B 树类索引。多数场景默认用的还是 B 树类。另外，数据库做哈希连接（hash join）时，把一张表的连接列建成哈希表，再逐行去查另一张表。
- 缓存和去重：缓存按键存取（LRU 缓存里的「键到节点」映射就是哈希表，见目录中的「LRU 缓存」）；去重用 `HashSet`，把元素逐个放进去，已经在里面的就是重复；经典题「两数之和」用 `HashMap` 记下见过的数，把 O(n²) 降到 O(n)。

## 6. 关卡建议

### 看

主画面：图书馆，墙上一排编号书架（容量 7）。管理员拿到一本书，书脊上有书号（整数）。画面讲四件事，每画面最多一行字：

1. 没有哈希时：管理员从第一个书架一个个找，来回跑（与顺序查找「一个个找小熊」对照，点到为止）。
2. 有了规矩：书号除以 7 的余数就是书架号，管理员一步走到。
3. 两本书撞了同一个书架，书架上多出一摞（链地址法）。
4. 另一种办法：这格满了，往旁边一个书架放（线性探测），取书时也同样一格格往后看，看到空架才说「没有」。

动画由引擎的轨迹生成：算余数、走到书架、比对书号、往下一格。末页可提一句「书太多了就换大书架，每本重新排」。

### 玩

两个小游戏，孩子当管理员，图标为主，答案固定，做错给提示（晃一下、书架透光），不说「错了」。

- 玩法一「直接走到书架」：书上有大数字书号（如 10、23、31），书架在墙上围成一圈，编号 0 到 6。孩子点书架放书；提示通过「数一圈」引导：书号是几，就从 0 号架起一格格数几下，数到哪停下就是书架（数过 6 号就回到 0 号）。几轮后再把「数几下」换成点一下的「余数」按钮，让孩子发现「数一圈剩下几格」就是答案。目标是让孩子说出「书号决定放哪个书架」，不要求会写取余。
- 玩法二「撞了同一个书架怎么办」：孩子放的书恰好撞上已有的书，书架摇晃，弹出两个选择图标：「叠在一起」（链地址法）或「放到旁边空架」（线性探测）。两种选法都能继续玩，之后让孩子取书，看两种方法各要多走几步。目标是让孩子体会：撞了也有办法，而且书越多撞得越多。

### 做

**猜下一步**（连对 5 次过关，建议用容量 7、整数键）

- 题型一：给出键和当前表状态，点出它该落在哪个桶（含负数键，对应易错点 1）。
- 题型二（线性探测）：键的目标桶被占了，点出它最终放进哪个桶（含回绕，对应易错点 3）。
- 题型三：查找一个键，点出下一个要看的桶，或点出「到这里就能断定不存在」的桶。
- 答错解释写在引擎 `why` 里，如「7 % 7 = 0，它的目标是 0 号桶，被占了，看 1 号」。

**找 bug**（三个坑，每个一段 Kotlin 代码、一组固定输入，点出错的那一行）

1. 删除时直接置空（线性探测，对应易错点 2）：输入 `put(1), put(8), remove(1), get(8)`（容量 7，两者同在 1 号桶）。预期得到 8，有坑的版本找不到。
2. 负数取模（对应易错点 1）：`val i = key % cap`，输入键 -3、容量 7，下标变成 -3，数组越界。修正为 `Math.floorMod(key, cap)`。
3. 扩容后不重新计算桶号（对应易错点 4）：容量 4 扩到 8，键 5 原来在 1 号桶，搬迁后仍放 1 号桶，而按新容量应在 5 号桶，之后 `get(5)` 找不到。

备选：`put` 没先检查键已存在（易错点 5）、探测不回绕（易错点 3）。

**亲手写**（建议 Kotlin 包 `hashlookup`，固定哈希函数 `key % capacity`，键值都是 `Int`，不依赖遍历顺序）

主函数：链地址法的哈希表。

```kotlin
class ChainedIntMap(private val capacity: Int = 7) {
    val size: Int
    fun put(key: Int, value: Int)    // 键已存在则更新
    fun get(key: Int): Int?          // 不存在返回 null
    fun remove(key: Int): Boolean    // 删除了返回 true
    fun bucketOf(key: Int): Int      // 桶号，负数键也要在 0 until capacity 内
}
```

变种：线性探测，带墓碑的删除。

```kotlin
class ProbedIntMap(private val capacity: Int = 7) {
    fun put(key: Int, value: Int): Boolean  // 表满且键不存在时返回 false，不能死循环
    fun get(key: Int): Int?
    fun remove(key: Int): Boolean
}
```

测试点：

- `bucketOf(15) == 1`、`bucketOf(-3) == 4`（容量 7）。
- 键已存在时 `put` 是更新，`size` 不变。
- 取不存在的键得到 `null`。
- 容量 7，键 1、8、15 三个同桶，都能取到；删掉 8 后 1 和 15 仍能取到。
- 链地址法：`remove` 一个不存在的键返回 `false`。
- 线性探测：键 6、13 同桶，13 落在 0 号桶（回绕）；删掉键 1 后，排在它后面的 8 仍能取到（墓碑）；删除后再插入可复用墓碑位置，`get` 仍正确；容量 3 放满 3 个键后，再 `put` 新键返回 `false`，再 `get` 一个不存在的键不死循环。
- 随机操作序列与 Kotlin 自带 `HashMap` 对拍，每步结果一致（独立标准答案）。

### 延伸

- 复杂度：为什么平均 O(1)、最坏 O(n)；负载因子与扩容、摊还。
- 为什么哈希表不能范围查询、没有大小顺序。
- 真实世界：`HashMap`（桶数 2 的幂、链长转红黑树）、Redis 渐进式 rehash、数据库哈希索引与 B 树的分工、缓存与去重。

### 与顺序查找（linear-search）的分工

- 顺序查找：不要求有序，一个个比，O(n)。哈希查找：不要求有序，算桶号一步到位，平均 O(1)，代价是多占空间、不保持顺序、要处理冲突。
- 「看」的开头可以直接接顺序查找的画面（同一个图书馆里管理员一个个找），但本关不重复讲顺序查找，只用一句话和一个画面做对照。
- 二分查找要求有序、O(log n)，哈希要求哈希函数好、平均 O(1)；延伸阅读里可以一句话对比三者。
