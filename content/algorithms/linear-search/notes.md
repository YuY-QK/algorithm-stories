# 顺序查找：资料

## 1. 解决什么问题

在一组**不要求有序**的数据里，找到某个值第一次出现的位置，或者确定它不存在。

## 2. 核心思路

1. 从第一个元素开始，用下标 `i` 指着当前要看的那个。
2. 比较 `arr[i]` 和目标。
3. 相等就找到了，返回 `i`。
4. 不相等，`i` 加 1，看下一个。
5. `i` 走出末尾还没遇到，说明不存在，返回「找不到」的约定值（常见是 `-1`）。

## 3. 复杂度和性质

| 项目 | 值 |
|---|---|
| 时间（最好） | O(1)，目标就在第一个 |
| 时间（平均） | 目标存在且每个位置等可能时，平均比较 (n+1)/2 次，O(n) |
| 时间（最坏） | O(n)，目标在最后一个或不存在，比较 n 次 |
| 空间 | O(1) |
| 前提 | 无。无序、有序都行；数组、链表都行（只需要能从头往后一个个走） |

- 「稳定性」是排序的概念，查找不涉及；对应的问题是**有重复元素时返回哪一个**：从前往后扫，天然返回第一个。
- 找不到是最慢的情况，必须把每一个都看完才能下结论。
- 不用预处理，不用额外内存，数据变了也不用重建任何东西。

## 4. 常见变种和易错点

**变种**

- 哨兵版：把目标临时放到末尾当「哨兵」，循环里就不用每次检查 `i < n`，每个元素只做一次比较（普通版是两次：下标越界检查加相等比较）。扫完后把原来的末尾元素放回去，再判断是在真实位置找到的，还是只撞上了哨兵。Knuth《计算机程序设计艺术》第 3 卷 6.1 节讲顺序查找时介绍过这个技巧。
- 找最后一个出现的位置：从后往前扫，或者扫完整个数组并记录最近一次命中。
- 找所有出现的位置：不在第一次命中时返回，把下标收集起来。
- 按条件找（`find { it > 10 }`、`indexOfFirst`）：把「相等」换成一个判断函数。
- 有序数组上的提前停止：遇到比目标大的元素就可以断定不存在，不必扫到底（最坏仍是 O(n)，但不存在时平均少看一半）。
- 链表上的顺序查找：只能沿 `next` 一个个走，无法用下标跳。

**易错点**

1. **找不到时的返回值和下标冲突**：返回 `0` 当「没找到」，会和「在第 0 个位置找到」混在一起。约定 `-1`（或返回可空的 `Int?`），并且调用方必须检查，别把 `-1` 直接当下标用。
2. **找到后忘记 `return`**：循环里命中了只记下标却不停，结果变成「最后一个」；或者命中后继续往下走，最后落到末尾的 `return -1`。有重复元素时，应该在第一次命中就返回。
3. **越界**：写成 `for (i in 0..arr.size)`（Kotlin 的 `..` 含右端点），最后一轮读 `arr[arr.size]` 抛异常；应该用 `0 until arr.size` 或 `arr.indices`。
4. **返回值和比较用错**：返回了元素本身 `arr[i]` 而不是下标 `i`，目标是 0 时更难看出错。
5. **空数组**：循环一次都不进，应该直接落到「找不到」；有人在循环前先读 `arr[0]` 就会出错。
6. **哨兵版**：忘了把被覆盖的末尾元素放回去，数组被悄悄改坏；或者目标恰好等于原末尾元素时，没区分「真找到」和「撞上哨兵」，把撞哨兵误判成找到（要判断 `i < n - 1 || arr[n - 1] == target`）。哨兵版还要求数组可修改，且多线程下不安全。
7. **用 `==` 比较引用类型**：比较的是对象身份还是内容，要看语言（Java 里字符串用 `==` 就是典型的坑；Kotlin 的 `==` 调用 `equals`，不是这个问题）。

## 5. 和二分查找的对比

| | 顺序查找 | 二分查找 |
|---|---|---|
| 数据要求 | 无 | 必须有序，且能按下标随机访问 |
| 时间 | O(n) | O(log n) |
| 预处理 | 无 | 需要先排好序（排序本身至少 O(n log n)） |
| 数据结构 | 数组、链表都行 | 数组行，链表不行 |

什么时候顺序查找反而更合适：

- **只查一次、数据无序**：先排序再二分，比直接扫一遍还慢。
- **数据很少**：二分省下的比较次数很有限，顺序扫描代码更简单、不容易写错。具体多少个元素以内顺序更快，取决于语言、硬件和数据，没有通用数字，要实测（不在这里编数字）。
- **链表**：不能按下标跳到中间，二分用不上。
- **数据经常变**：数组要保持有序，每次插入删除都要挪动元素。
- **找的条件不是「等于某个值」**：比如「第一个满足某个条件的」，数据本身没有可二分的顺序。

数据又多、又要反复查，则应换结构：先排序后二分，或者用哈希表（见 `hash-lookup` 关卡，这里不展开）。

## 6. 真实应用

**生活**

- 在一排没整理的抽屉、玩具箱里翻找东西：一个个打开，找到就停。
- 在一份没排序的名单或购物小票上，从头往下看有没有某个名字或某样东西。

**工程**

- 各语言标准库里的 `indexOf`、`contains`、`find`：Java 的 `ArrayList.indexOf` / `contains`、Python 的 `x in list` 和 `list.index`、JavaScript 的 `Array.prototype.indexOf` / `find`、Kotlin 的 `indexOf` / `first { }`，对无序列表做的都是从头到尾的扫描，复杂度 O(n)。Python 的 `list.index` 找不到时抛 `ValueError`，JavaScript 的 `indexOf` 找不到返回 `-1`，两种「找不到」的约定都很常见。
- C 标准库里的 `strchr`、`memchr` 在字符串、内存块里找某个字节，本质也是顺序扫描。
- 数据库没有可用索引时的全表扫描：PostgreSQL 的 `EXPLAIN` 里显示为 `Seq Scan`，逐行检查条件。表很小时，规划器选顺序扫描也是常见的合理选择（官方文档的 Using EXPLAIN 一节有例子）。
- `grep` 在文本里查找字符串，是逐行、逐字符地扫描（具体实现里有更快的字符串匹配算法，但没有索引时必须看完整个输入这一点和顺序查找一致）。

## 7. 关卡建议

### 看

故事：一排 8 个玩具箱，小熊藏在其中一个里。

- 画面 1：一排盖着盖子的玩具箱，小朋友站在最左边，头顶一个小箭头（下标 `i`）。
- 画面 2：打开第 1 个，里面是积木，盖上，箭头右移。
- 画面 3：再开几个，每次都是别的玩具，开过的箱子保持半透明「看过了」。
- 画面 4：打开某一个，小熊跳出来，箭头停住，后面没开的箱子不再开（强调「找到就停」）。
- 画面 5：换一排没有小熊的，开到最后一个，空的，小朋友摊手（引出「没找到也要全看完」）。

箱子不要排大小或编号顺序，让孩子看出「没有规律，只能一个个来」。

### 玩

玩法一「开箱子找小熊」（孩子当主角）：

- 程序把小熊藏好（答案固定，盖住）。孩子点箱子，箱子打开，露出玩具；不是小熊的箱子留下一个「看过了」的小标记。
- 提示（不说错）：点已经开过的箱子，箱子晃一下，小熊图标在旁边摇头；想跳着开时，没有任何提示（因为跳着开本来就合法），但结算时显示开了几个箱子。
- 几局之后，问「小熊在最后一个的时候，要开几个？」「小熊不在的时候呢？」让孩子自己说出「最坏要全开」。
- 次数越少星星越多，但小熊位置是随机的，所以星星看的是「有没有重复开、有没有找到后继续开」，不奖励运气。

玩法二「藏小熊」（孩子出题，看机器人怎么找）：孩子选一个箱子藏小熊，小机器人从左往右一个个开，孩子看它开了几个；再选「不藏」，看机器人把所有箱子开完。学到的是「位置越靠后越慢，没有最慢以外的捷径」。

玩法二可选：同样 8 个箱子，另有一排按大小排好的箱子，问「这一排是不是可以少开几个？」，作为通向二分查找的铺垫（不强求孩子回答）。

### 做

1. **猜下一步**：给出当前 `i`、目标和已开过的箱子，让用户点：
   - 下一步会看哪个下标；
   - 当前这个比较的结果会让循环「继续」还是「返回」；
   - 终止时返回什么（下标或 `-1`）。
   题目要包含：目标在第 0 个、在最后一个、不存在、有重复元素（返回第一个）这几类，连对 5 次过关。

2. **找 bug**（三个真实的坑，每个给一段有错的 Kotlin 和一个会暴露它的输入）：
   - 坑一：`for (i in 0..arr.size)`，目标不存在时读 `arr[arr.size]` 越界。点出 for 那一行。
   - 坑二：没找到时 `return 0`，输入目标不存在的数组，调用方把 `0` 当成「在第 0 个位置」。点出返回那一行。
   - 坑三：命中时不 `return` 而是 `found = i` 继续扫，有重复元素时返回的是最后一个而不是第一个。点出赋值那一行，输入如 `[3, 7, 3]` 找 3，应该返回 0，却返回 2。

   备选坑：哨兵版忘记还原末尾元素；空数组先读 `arr[0]`。

3. **亲手写**（本地 Kotlin，建议包名 `linearsearch`）：
   - 基础函数：`fun linearSearch(arr: IntArray, target: Int): Int`，找不到返回 `-1`。
   - 变种：`fun lastIndexOf(arr: IntArray, target: Int): Int`（最后一个出现的位置），或者 `fun linearSearchSentinel(arr: IntArray, target: Int): Int`（哨兵版，行为和基础版一致，且测试里检查调用后数组内容没变）。建议做哨兵版，因为它要求处理还原和「真找到 vs 撞哨兵」。

   测试点：
   - 空数组，返回 `-1`；
   - 单元素，命中和不命中；
   - 目标在第一个、在最后一个、在中间；
   - 目标不存在；
   - 有重复元素，返回第一个下标（如 `[3, 7, 3]` 找 3 得 0）；
   - 目标等于 0 或为负数（防止用 `0` 当「找不到」）；
   - 哨兵版：目标等于原末尾元素、目标不存在、调用后数组不变；
   - 随机数组，结果和 Kotlin 自带 `indexOf` 对比（独立的标准答案）。

4. **挑战**：给一排箱子，问「最坏要开几个」「平均要开几个」，让用户在 1 到 n 之间猜，再用若干局统计验证。也可以做对比：同一份有序数据，顺序查找和二分查找各开几个，让用户感受 n 变大时差距拉大（参考二分关卡的挑战）。

### 延伸阅读

- 复杂度：最好 O(1)，平均 (n+1)/2 次，最坏 n 次。
- 和二分查找的对比表（见第 5 节）。
- 哨兵技巧为什么只省常数倍，不改变 O(n)。
- 各语言 `indexOf` / `contains` 的实际用法，和 `Seq Scan` 的例子。
- 下一站：想更快就先排序再二分，或者用哈希（`hash-lookup` 关卡）。
